# 需求与验收翻译官

## 第 0 步：入口闸门（不跳过）

1. 这是不是一个"需求/方案"？否 → 纯润色即止，不套骨架。
2. 规模判定：
   - 模块 = 一个独立交付的脚本或表对象。清点口径：元数据/控制/配置类写入计入其服务的交付对象，不单独计数；既有脚本/调度的登记式接入（不改其结构）不单独计数。
   - 跨系统 = 改动落在 2 个及以上独立服务（如库 A 与库 B）上，且需要分别验证。
   - 选型 = 需要在 2 个及以上技术方案之间取舍。
   模块 ≤3、不跨系统、无选型 → 轻量；其余全量。
   轻量模式只省独立文件，不省步骤：
   - 第 3 步的结论以"FM 映射"一节写进 acceptance.md 开头。会踩、不踩都要列，各附一句理由。
   - 不产出独立的 failure-map.md。
   - 第 4 步、硬规则 2 改为对照这一节。
3. 业务域：查 glossary.yaml → 命中 = 本领域包覆盖的域，用本包；未命中 → 只用通用骨架并声明"域外，验收标准置信度低"，并在 intent.md 顶部放置高亮警示块："⚠️ 域外·需人审：本单无既有领域 skill 覆盖，验收标准置信度低，请人工审核确认后再交付使用"（run-note 第 0 步判定同步标注该警示）。

## 第 1 步：还原意图 → intent.md

- 一句话复述："你真正想要的是 ___"
- 四要素：谁用 / 做什么决策 / 时限 / 一个真实样例。每个要素标来源：原话 / 他人补全（补全人须具名到人——姓名或岗位；"需求方随附材料"不算具名，按补全人不明处理）/ 推导（写明从哪条原文推出）。
  - 谁用 = 人或角色，不能是脚本或系统。把链路、系统、脚本包装成"××执行者""××使用者""××负责人"仍不算人或角色；原文推不出可具名的真人或岗位（姓名/职务）→ 不合格，并入确认包。推导只能还原原文已有的指称，不能无中生有出角色。
  - 来源标注造假（给包装/编造的角色标"原话/原文"）比漏标更重，直接判不合格并记评分事故。
  - 时限 = 绝对日期，或可换算成绝对日期的写法。
  - 样例 = 内容可读；只有一个读不到内容的引用不算。
  缺失、不合格、补全人不明的要素 → 合并成 1 个确认包，不编。

## 第 2 步：术语标准化 → spec.md

- 查 glossary.yaml 出映射表（用户原话 | 行业术语 | 所属环节 | 说明）
- 用户已用标准术语 → 原样保留，只补所属环节
- spec.md 写：目标 / 边界 / 非目标
- 术语表落盘：第 2 步产出的映射表（含未命中词条及其所挂升级包编号）另存一份到**所在项目的专门术语收录目录**——项目根目录下的 `terms\` 文件夹（无则新建，跨单累积共用）：产物目录位于某项目根之下时落项目根\terms\；未约定项目根（散用单开目录）时落产物目录\terms\。文件名须人能读懂：`术语表-第N单-〈主题〉.md`（N 按目录内已有表顺延；主题＝需求一句话缩写，如〈表X〉增量采集）；项目有名称时加前缀 `〈项目名〉-术语表-第N单-〈主题〉.md`。表尾注明来源单、日期与本轮小结（如"新增映射 6 条、未命中 2 条挂 E-xx"）。该目录是项目的大白话→术语逐单记录，供跨单查阅；术语权威仍是 glossary.yaml——查不到的词条照样走升级包，不得以 terms\ 旧表替代或自造。轻量/全量两种模式均产出。

查 glossary.yaml 时同步确认 specs 目录是否含验收断言形态卡：含则将其列为第 4 步必读输入并在产出中声明"已对照形态卡"；不含则声明"无形态卡"。禁止跳过确认直接进入第 4 步。

## 第 3 步：失败模式映射 → failure-map.md

读领域包 specs/failure-modes.md，逐条判断"本任务会不会踩到这条"：
- 会踩的 → 记入 failure-map（模式编号 + 本任务的具体表现）
- 本任务特有的新错法 → 追加到 failure-map 并标 [新]，复盘时回填主清单

## 第 4 步：三层验收 → acceptance.md（本 skill 的核心产出）

为 failure-map 里每条配检查，三层压满：

| 层 | 写法 | 硬规则 |
|---|---|---|
| 机械层 | 可脚本判定：对账 diff=0 / 重跑 count 不变 / 断言/字节数/端口探测。每条给脚本路径或可直接执行的命令 | 能写脚本的绝不写成文字；每条标它杀的 FM-xx |
| 语义层 | 独立复核可逐条 pass/fail 的断言，附"判定证据在哪" | 不写"仔细检查"这类词 |
| 人判层 | 口径/重要性选择 → 每条生成升级包 | ≤3 选项，各带代价/风险 + 推荐，5 分钟可裁决 |

### 机械层 TBD 规则

机械层命令允许含占位符，格式只能是两种：
- <TBD:E-编号>：等升级包裁决。该编号的升级包"阻塞"栏必须列出本条 M 编号。
- <TBD:缺材料:说明>：材料缺失，裁决补不出来。必须同时出一个面向流程维护人的升级包，按标准缺口处理，不准挂起空等。

调用参数变量（由执行验证者在运行时代入的分区日期等，如脚本子命令参数）不属于 TBD，但不得承载待裁决值——凡值待裁决的占位符一律走两种 TBD 格式。

没挂到编号上的 TBD 一律视为未通过。
TBD 的补齐值只能来自升级包的裁决记录。补齐时，在 acceptance.md 该行注明"取值依据：E-编号 裁决"，执行方不得自填。

### 验收性陈述落条目规则

spec.md 与前序步骤中出现的每一句验收性陈述（目标/边界里"一致、不变、可验证"类承诺），必须在 acceptance.md 落成对应编号条目（机械层或语义层），不允许只停留在叙述。

领域包 specs 含验收断言形态卡时，每条机械/语义验收条目的形态（比较对象、分区口径、阈值、是否直比等）逐条对照形态卡；命中禁止形态清单（如以全历史合计替代当日分区直比）= 未通过，回第 4 步。形态卡不改变"分不清出升级包"的纪律——形态卡未覆盖的场景仍走升级包。

## 第 5 步：交付前自检

| 检查项 | 未通过 → 回到 |
|---|---|
| 每条机械层标准都能落成可执行命令/脚本（占位符仅限 <TBD:E-编号> 或 <TBD:缺材料:说明> 两种）？ | 第 4 步（出口规则见下） |
| spec.md 目标/边界及前序各步中的每一句验收性陈述（对账口径、覆盖面、数据一致性声明），acceptance.md 都有对应 M/S 条目？ | 第 4 步 |
| 每条标准都标了杀的失败模式编号？ | 第 4 步 |
| 人判层都成了升级包而不是开放式问题？ | 第 4 步 |
| 四要素齐、来源已标、他人补全项已确认（补全人已具名）、无编造默认需求（谁用不得以链路/系统包装充数）？ | 第 1 步 |
| 建议/可选模块留 TBD 而不是编细节？ | 第 2 步 |
| 术语表已按第 2 步落盘项目术语目录 terms\（命名含轮次与主题、含未命中词条与其所挂升级包编号、表尾有本轮小结）？ | 第 2 步 |
| 判域外时：intent.md 顶部已放"⚠️ 域外·需人审"高亮警示块且 run-note 同步标注？ | 第 0 步 |
| 产出全中文？（命令、表名、标识符除外） | 全文 |
| 产出中无明文凭据（命令行参数未展开密码）？ | 第 4 步 |

### 机械层行出口规则

机械层行未通过时：
- 未通过的原因全部是 <TBD:E-编号> → 状态记为"挂起待裁决"，写入 state.json（列出挂起的 M 编号和对应 E 编号），不回第 4 步。裁决回来后补齐，然后重跑第 5 步。
- 有其他原因 → 回第 4 步，最多 2 次；超过次数按 dw-delivery.yaml 的 on_exceed: escalate 处理。

挂起期间，acceptance.md 不得交给 IR-review。

豁免（人审裁决约定）：acceptance.md 因 <TBD:E-编号> 裁决补齐而发生的变化，视为对原裁决对象的执行细节填充，不构成裁决对象变化——原 Gate 签字继续有效，不触发重签。但补齐值若改变口径本身（与拍板相反或引入拍板时不存在的新口径），仍须重签并留痕 state.json。

四要素行未通过且原因全部是"待需求方确认"时：状态记为"awaiting_reply"写入 state.json（列确认包编号与涉及要素），不回第 1 步；期间 intent 相关字段按待确认处理，不得编造默认值。需求方答复后补全并重跑第 5 步。

## 升级包格式

编号：E-YYYYMMDD-NN；流程问题用 EP-YYYYMMDD-NN，不计入单子预算。
确认包（四要素等待需求方补全的口径包）属任务级：E- 编号、计入预算、阻塞栏写所涉要素；不使用 E-/EP- 之外的任何前缀。
预算记账以包为单位（"第 n/3"指包数），不得按选项拆分计数；选项 ≤3 为硬约束，超限即未通过。

| 字段 | 要求 |
|---|---|
| 问题 | 一句话 |
| 冲突/缺口依据 | 引用材料原文 |
| 杀 | FM-xx |
| 阻塞 | 列出被阻塞的 M/S 编号；无则写"不阻塞" |
| 选项 | ≤3，每个写代价/风险；材料中有直读解（如已点名的列/方式）时必须入选 |
| 推荐 + 依据 | 依据引用材料原文；所推荐选项（含兜底项）如命中材料已列明的风险，必须标【已知风险】 |
| 本单预算 | 第 n/3 个；超出时同时写归因 A 类说明 |

裁决前：被阻塞项挂起（见第 5 步出口规则）；不阻塞的部分可以继续做，但不得通过任何 Gate。

## 硬规则

1. 分不清就升级包，不默默选。环境/资源状态与需求诉求矛盾（如目标环境处于关机、停用、授权受限状态而需求要求其持续运行）即属"分不清"：出升级包，不得以白名单断言、直读锁定等方式单侧锁定目标域。
2. 没有对应失败模式的检查不写（防臃肿）。
3. 验收标准 = 合同：Reviewer 只看 acceptance.md + 原始需求 + 产出物，不看任何执行过程陈述。
4. 凭据不得进入产出物：intent/spec/acceptance/升级包中禁止出现密码明文，也不得在命令行参数里展开密码。
   凭据以该工具的原生文件机制传递（如数据库客户端→defaults 文件、批量导出工具→password 文件，其余工具照此类推），不得混用其他工具的旗标；
   命令行展开类写法（如 -p"$变量"、$(cat 文件) 结果进入 argv）一律禁止——注释声明"符合硬规则 4"不豁免实文违例；
   不确定某工具的原生机制时出升级包问，不猜。
   环境变量中转仅限工具确无文件机制时使用，且须在 acceptance 注明。
   glossary 中如有明文，只取其文件路径，不得转抄。
